### 结论：两个赛道冷热差距是数量级的

- **排版赛道是红海**：692 个仓库，头部 13k 星，还在持续有人做。在这个方向做"又一个 Markdown 排版器"没有任何机会，论文也没有创新点可写。
- **文风迁移赛道近乎空白**：`style imitation` 23 个、`author imitation` 21 个、`style transfer + writing` 34 个，**加起来不到 80 个，且星数全在两位数以下**。学术界有成熟综述（中文信息学报 2025 有专门的《文本风格迁移综述》），但**工程落地几乎没人做**。

> **这组数字是本项目最值钱的一张牌。** 它同时证明了"方向选得准"（毕设选题价值）和"有空白可填"（创新点存在性）。

## 三、转毕业设计：先做体检

### 3.1 对照评分表（综合多校公开细则）

| 评分维度 | 权重（参考） | 你现在能拿几分 | 缺什么 |
| --- | --- | --- | --- |
| 选题价值 | 10% | **高**（真实痛点 + 赛道空白） | 需要文献支撑证明"空白"，见第一节 |
| 工作量 | 25% | **中高** | 代码 4543 行达标；但**没有数据库、接口少、单页面**——评审口径常按"表数/接口数/页面数"衡量，这是硬缺口 |
| 技术应用 | 25% | **中** | 技术栈单一（无框架、无数据库）；**没有实验对比**，学术深度不足 |
| 文档质量 | 20% | **待补** | 论文还没写；好在有 README + 规划书 + 本手册当素材 |
| 答辩表现 | 20% | **高**（能讲清取舍） | 需要准备演示与现场答疑 |

### 3.2 五个必须补的缺口

**缺口 1：没有数据库（最致命）**

绝大多数高校的评分细则里都有"数据库表 6–10 张、后端接口 15–25 个"这类隐含口径。你现在数据全在浏览器 localStorage + 文件系统里，评审老师会直接判定"工程完整性不足"。

**缺口 2：没有实验对比（学术核心）**

现在是"我觉得生成得像"，没有量化。毕设的 40 分专业能力里，"得到合理有效的结论""体现创新意识"都要靠实验撑。**没有实验 = 没有论文。**

**缺口 3：技术栈单薄**

零依赖是产品上的优点，但在毕设语境里是"技术应用 25% 拿不满"的原因。需要引入一个正经的后端框架和数据库层。

**缺口 4：题目还没起**

毕设题目有惯例公式：**技术 + 场景 + 问题类型**。不能叫"公众号风格工坊"。

**缺口 5：没有正式的文献综述**

论文必须收集中外文献追踪研究现状。好消息是：这个方向的综述论文是现成的，见第七节。

## 四、改造方案

### 4.1 题目（给三个候选）

按"技术 + 场景 + 问题类型"公式：

1. **基于大语言模型检索增强的公众号文风迁移系统设计与实现**（推荐）
   - 技术：LLM + 检索增强（RAG 思路的 few-shot 变体）
   - 场景：公众号内容创作
   - 问题：文风迁移

2. **面向个人创作者的风格量化与个性化文本生成方法研究及系统实现**
   - 偏研究方法，适合导师偏学术的情况

3. **融合风格画像与范例检索的中文自媒体文本生成系统**
   - 覆盖面更广，答辩时解释成本更低

**选题来源要提前想清楚**：多数学校把选题分为科研项目 / 生产实践（社会实际）/ 自拟三类，且自拟比例常有限制。你这个项目最好挂靠在"生产实践"——**说明有真实使用者（自媒体运营），是解决社会实际问题的**。这也是为什么第 6 节"找真实用户"那一项必须在选题前完成。

### 4.2 系统架构改造

```
表现层   前端（拆成 6-8 个功能页：账号管理 / 文章抓取 / 风格分析 / 风格档案 /
         内容生成 / 素材管理 / 效果评估 / 系统设置）
         ↑ HTTP (20+ 接口)
服务层   后端框架（Flask / FastAPI，从 serve.py 迁移）
         ├── 抓取服务（保留现有重试+快照）
         ├── 分析服务（六层画像，现有 profile* 函数迁移过来）
         ├── 生成服务（提示词编排 + 三重校验回退）
         └── 评估服务（新增，实验用）
数据层   关系数据库（MySQL 或 SQLite）+ 文件存储（图片、快照）
```

**建议的表设计（11 张，够撑工作量）**：

| 表 | 作用 | 为什么评审喜欢 |
| --- | --- | --- |
| `account` | 公众号/账号 | 主表 |
| `article` | 抓取的文章元数据 | 与 account 一对多 |
| `article_snapshot` | 原文 HTML 快照 | 与 article 一对多 |
| `style_profile` | 风格档案主表 | 关联 account |
| `profile_layer` | **六层画像拆表存**（layer_name / metrics JSON） | 便于按层统计查询 |
| `image_asset` | 图片（md5、宽、高、分组） | 去重逻辑在库层面可查询 |
| `image_group` | 图片分组 | 多表关联 |
| `generation` | 生成历史（提示词、结果、字数） | 与 profile 关联 |
| `generation_metric` | 每篇生成稿的量化指标 | **评估实验的数据源** |
| `evaluation` | 盲评记录（评委、得分、偏好） | 实验表，答辩亮点 |
| `fetch_log` | 抓取日志（成功/失败/重试/快照回落） | 证明稳健性设计 |

关键：`profile_layer` 与 `generation_metric` 两张表让"六层画像"和"效果评估"变成**可 SQL 查询的数据**，能出图、能出统计表——论文里的图表就有了。

**接口从现有 ~10 个扩到 22 个左右**：账号 4 个、抓取 4 个、分析 3 个、档案 4 个、生成 3 个、素材 3 个、评估 2 个、系统 2 个。

#### 落地情况（2026-09-16：已按此方案实现）

| 项 | 方案 | 实际落地 | 差异说明 |
| --- | --- | --- | --- |
| 数据库 | MySQL 或 SQLite | **SQLite**（`db.py`，标准库 `sqlite3`） | 保住"双击即用、零安装"。答辩机器上跑不起来 MySQL 是灾难；论文里写"轻量级嵌入式关系数据库"完全站得住 |
| 表 | 11 张 | 11 张，一张不少 | `profile_layer` 六层拆表、`generation_metric` 指标表都已可用，能直接出统计表 |
| 接口 | 22 个 | 25 个（含原有 health/version 等） | 账号、档案、分析、生成、指标、评估、素材、日志全覆盖，含 PUT/DELETE |
| 后端框架 | Flask / FastAPI | **不迁**，仍是标准库 `http.server` | 零依赖优先；架构章节写"轻量 HTTP 服务层 + 独立数据访问层（db.py）"，分层依然清晰 |
| 迁移 | — | 首次启动自动把 `articles/*/index.json` 导入库 | 实测导入 28 个分组 / 27 篇 / 1143 张图；无 index.json 的目录也会建组并扫目录补图 |

前端采取**双层存储**：SQLite 为真源，localStorage 为离线缓存。启动时以库为准覆盖本地，保存后异步回写，接口挂了静默降级。API Key 不入库（README 对用户的承诺不能破）。

E-R 图与表结构说明见 `db.py` 顶部注释与 `SCHEMA`，论文第 4 章可直接照抄。

### 4.4 实验设计（这是从"项目"变成"论文"的关键）

**实验一：效果对比（主实验）**

| 组别 | 提示词配置 | 对应学术分类 |
| --- | --- | --- |
| 基线 A（Generic） | 只给主题，通用提示 | zero-shot |
| 基线 B（仅参数） | 风格参数描述 | prompt-based |
| 基线 C（参数 + 黑名单） | 参数 + 约束 | prompt-based 增强 |
| 本文方法 | 六层参数 + 检索锚点 | prompting + memory-augmented |
| 上界参考 | 原文（供评委校准） | — |

**实验二：消融实验**——逐层去掉六层画像，看哪一层贡献最大。这个实验很有价值，因为学术界对"选题/认知层能否被量化"是有争议的，你的数据无论正反都是结论。

**实验三：人工盲评**——把 4 组生成稿去掉来源标记后混排，请 10–20 人（含若干公众号运营者）按"像不像同一作者写的"打分排名。复用 style-retrieval 的实验范式，可直接和它的数据对比。

**评价指标（三档，缺一不可）**：

1. **风格相似度（客观可计算）**——这是你最大的方法论亮点：
   - 段长分布 KL 散度 / 直方图重合度
   - 句长标准差、平均句长偏差
   - 连接词密度偏差（"然而/因此/首先"等）
   - 图文节奏偏差、表情密度偏差
   - 话题分布重合度、论据类型占比偏差
   
   > **同一个量化体系既用于生成约束、又用于效果评估**——这在方法论上是自洽的，写进创新点非常有说服力。而且这些指标全部可复现，不依赖主观判断。

2. **内容质量（客观）**——字数达标率、标记完整率、改写回退率（你的三重校验天然产出这组数据）
3. **人工评价（主观）**——盲评排名、偏好比例

**数据集**：抓取 5–10 个风格差异明显的公众号，每号 10–20 篇。现在 `articles/` 里已有 1170 个文件的基础，扩展成本低。

### 4.5 创新点提炼（写进摘要和绪论）

1. **提出可计算、可审计的六层风格量化口径**，覆盖现有工作少有触及的"选题逻辑"与"认知框架"层，针对 LLM 难以模仿隐式写作风格的问题。
2. **参数约束与检索锚点双通道注入方法**，将提示工程与检索增强在文风迁移任务上结合，并通过对照实验验证其优于单一通道。
3. **生成后二次改写的安全机制**：三重校验（标记/字数/标题）+ 不达标自动回退，保证改写环节单调不劣化。
4. **同一量化体系复用于生成约束与效果评估**，形成"量化—生成—评估"闭环，解决文风迁移任务主观评价难的问题。

### 4.6 时间线（按 2027 年 6 月毕业推）

## 五、风险与坑

1. **选题来源**：如果你们学校对"自拟题目"比例有硬限制，务必提前跟导师确认——这个项目按"生产实践/社会实际"申报更稳（有真实使用者需求）。
2. **一人一题**：如果同组有人做类似方向，题目必须明确区分。
3. **别把"调用大模型 API"当成创新点**：评审老师对"调 API"极不买账。你的创新点在**量化方法 + 注入策略 + 校验机制**，一定要这样表述。
4. **实验不能省**：没有第 7 章的论文是"做了一个系统"，有第 7 章才是"做了一项研究"。这是及格和良好的分界线。
5. **中期后不能改题**，所以数据库和实验方案必须在开题前想清楚，不能边走边看。
6. **查重**：自己写的 README、规划书可以直接当素材，但**不能整段贴进论文**（含自引重复率），要重写表述。
7. **不要同时开发 APP 和后台**——多系统集成是毕设延期的高频原因。保持单系统。

## 六、立刻该做的三件事

按顺序：

1. **找导师谈题目**（本周内）。带着题库里那张赛道对比表去——用数据说明"这个方向是空白"，比口头描述有效十倍。
2. **完成选题来源所需的事实**：找 3–5 个真实用户，留反馈记录。这既是毕设"生产实践"来源的证明，也是简历权重最高的一项。
3. **抓够实验数据**：5–10 个公众号 × 10–20 篇，风格要拉开差距（技术号 / 情感号 / 吐槽号 / 教程号）。数据抓取越早越好，公众号文章会被删。
