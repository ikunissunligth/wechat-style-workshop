## 1. 定位：它能证明什么，不能证明什么

### 能证明

- **问题嗅觉**：你自己发现了"AI 写的公众号不像人写的"这个真实痛点，不是教程给的题。
- **方案判断力**：在"微调模型"和"提示词 + 检索范例"之间做了有依据的取舍，且能讲出依据（引用了开源盲评实验数据）。
- **把模糊需求变成可计算约束的能力**：这是核心亮点。"口语化一点"对模型不构成约束，你把它拆成了平均段长、最长段、图文节奏、黑名单词表。
- **交付能力**：功能闭环、有测试、有文档、有公开仓库——不是半成品。
- **对 AI 边界的理解**：知道模型会编造、会跑偏，所以设计了事实边界约束和三重校验回退。这一条在 2026 年特别值钱。

### 不能证明

- 框架/生态经验（无 React/Vue/Spring 等）
- 数据库、并发、分布式、部署运维
- 多人协作（无 PR、无 code review、无 issue 处理）
- 模型训练能力

**结论**：它是"能独立交付一个完整工具"的强证据，不是"能进工程团队写大型系统"的证据。所以——

> **不要让它当简历上的唯一项目。** 和 AIxiangji 搭配写：AIxiangji 证明移动端与工程深度，本项目证明 AI 应用落地与产品感。两份加起来的画像才完整。

### 2.2 作品集 / 项目详情页版

在作品集链接里放这个版本，讲清楚四件事：

**问题（S）**
通用大模型写公众号有三类硬伤：风格不可描述（"口语化一点"对模型不构成约束）、篇幅不可控（要两千给一千五）、配图排版全靠手。现成的开源工具只解决"写好了怎么排"，不解决"怎么写"。

**方案（T + A）**
1. **风格量化**：抓真实文章 → 按六层框架统计成参数（字号/字色/行距/对齐、平均段长/最长段/段长分布、图文间隔、装饰与表情密度、话题分布、切入角度、论据类型占比、高频价值判断句）。
2. **范例检索注入**：按段落用途（开篇/数据型论据/口语互动/短句成段/展开/收尾）挑真实段落作 few-shot 锚点，明确禁止照抄内容。
3. **约束生成 + 安全阀**：参数约束 + 黑名单 + 节奏要求 + 事实边界；生成后二次去 AI 味改写，三重校验不通过则回退。
4. **导出适配**：把微信后台的限制逐条反向变成规则。

**结果（R）**
- 全流程闭环，148 条测试通过（124 前端断言 + 24 端到端）
- 图池治理模块实测：998 张图检出重复 184 张、过小图 84 张
- 零依赖交付，运营同学双击即可用

**已知限制（主动写，加分）**
- 事实准确性依赖提示词约束，无法根除编造，价格/参数/引用仍需人工核对
- 单机部署，无协作与云同步
- 生成一篇长文约 2–3 分钟

> 主动写"已知限制"是高级信号。面试官见过太多声称完美的项目，承认边界 = 你真的做过。

## 4. 面试 Q&A 预案

### Q1 为什么不用微调模型做风格迁移？

三个理由，缺一不可：

1. **数据拿不到**。微调需要同一账号几十上百篇成对语料，普通用户手上就三五篇链接。
2. **和定位冲突**。微调要训练和部署，而我的目标用户是运营同学——交付形态是"下载 → 双击 → 打开浏览器"，引入训练链路这条路径就断了。
3. **不可解释**。用户会问"为什么这版像我"，微调答不上来；规则统计能把每一条约束指给他看。

补一句依据：style-retrieval 的盲评实验（罗素散文样本，4 个模型）显示，检索真实范例平均排名 1.74、纯参数描述 1.94、只给作者名 2.65、通用提示 3.67。**检索范例这条路的上限本身就高于"报风格名"，微调不是必需的。**

### Q2 风格量化为什么用规则统计，不用 embedding？

- embedding 相似度是个黑箱分数，用户看不到"哪里像/哪里不像"，也没法手动改。
- 规则统计输出的是**可直接转成提示词约束**的参数（平均段长 42 字、最长段 ≤120 字、每 4 段一图、禁用"首先/其次/综上所述"）。
- 而且不额外消耗模型调用、结果可复现、可写单元测试。
- 代价是覆盖不到语义层的微妙差异，这部分我用"模型提炼语气描述 + 真实段落锚点"来补。

### Q3 六层都实现了吗？怎么验证有效？

实现了。落地方式：
- 素材策略层：`profileArgument()` 统计论据类型占比（数字/引述/亲身经历/反问/口语词）
- 选题逻辑层：`profileTopic()` 用话题词典 + 切入角度正则统计，`topicBrief()` 只把占比 ≥25% 的写进提示词（阈值是为了避免长尾噪声污染）
- 认知框架层：`profileStance()` 抽取反复出现的价值判断句，最多 8 条

**验证方式要诚实说**：目前是靠人工比对生成稿与原文的主观评估 + 148 条自动化测试保证各层函数行为正确，**没有做盲评量化实验**。如果继续做，我会补一个盲评：把"原作者 / 本项目 / 通用提示"三版混排给评委排名——这也是我下一步想补的。

> 承认"没有盲评"比编一个数据强得多。而且你顺手给出了下一步方案，反而加分。

### Q4 index.html 快 3000 行，为什么不分模块？（大概率被问，必须准备好）

这是**刻意取舍**，不是疏忽：

- 目标用户是运营同学，不是工程师。交付形态是"下载 → 双击 start.bat → 浏览器打开"，一旦引入 npm install / 构建步骤，这条链路就断了。
- 单文件还带来一个实际好处：整个工具可以当附件发，跨设备零配置。

代价是可维护性，我用三招对冲：
1. `check.js` 做静态一致性检查——脚本语法、onclick 处理器引用的 ID 是否存在、动态创建 ID 的白名单。单文件最容易出的错就是"改了函数名忘了改 onclick"，这个检查专门堵它。
2. 124 条前端断言（jsdom 无头环境）+ 24 条端到端用例。
3. 业务逻辑按功能分区并统一命名前缀（profile* / *Brief / render*）。

**如果目标用户换成工程团队，我会拆成 ES Module + Vite，并把 Python 服务换成 FastAPI。**

> 最后这句是关键：证明你知道"什么时候该拆"，而不只是"我就是不想拆"。

### Q5 去 AI 味改写为什么需要三重校验？真出过问题吗？

出过。二次改写模型会"好心办坏事"——顺手改掉标题、删掉配图槽位标记、或者把 2000 字缩到 1500 字。这三类破坏都是**在提升文风的同时发生的**，单看文字质量反而变好了，所以必须单独校验。

三重校验：标记数量一致、字数落在目标区间、标题未被改动。任一不符 → 丢弃改写结果，用原稿。设计原则是**这个环节只允许变好，不允许变坏**。

### Q6 微信后台有哪些坑？你怎么发现的？

四个，都是实测踩出来的，不是看文档：

1. **垂直 margin 被忽略** → 段间距改用空 `<p>` 承载。
2. **只有 mp.weixin.qq.com 的链接可点击**，其余外链粘贴后连同网址一起丢 → 导出时转「文字 + [n] 角标」，网址收进文末【参考资料】纯文本保留。
3. **图片会被转存** → 导出时还原为原始 CDN 链接，而不是本地代理地址。
4. **排版细节不对称** → 我在 research/ 里存了真实文章样本做基准统计，发现图片**上方 0/46 篇插空段、下方 43/46 篇插空段**。这个不对称是看文档永远看不出来的，只能数。规则最后按这个基准反向校准。

> 第 4 点是这一题的杀手锏：它证明你是"数出来的"，不是"猜出来的"。

### Q7 抓取怎么做？失败和被删怎么办？

Python 标准库实现，无 requests 依赖。两层兜底：
- 单篇失败自动重试一次
- 每次抓取成功落盘原文 HTML 快照（`articles/_snapshots/`，按 URL 的 md5 命名）。文章被作者删除后，再次分析自动回落快照，并在界面上标注"来自快照"——不静默降级。

批量抓多篇时单篇失败不中断整体。

### Q8 图片为什么本地化，不接图床？

- 公众号会转存图片，图床外链在粘贴环节会被替换，本地池反而更可控。
- 用户能积累自己的素材库，按账号分组复用。
- 代价是池子会脏：所以做了图池治理——MD5 同字节去重 + 解析 PNG IHDR / GIF 头 / JPEG SOF 标记读宽高过滤小图（<200px），行内表情 ≤64px 豁免（否则会把 emoji 全误杀）。清理是**扫描只读、逐项勾选、确认才删**，删完同步重写 index.json。
- 实测：998 张图里重复 184 张、过小 84 张。

### Q9 有真实用户吗？效果怎么样？

**诚实答**：目前只有我自己用，没有外部用户，也没有量化效果评估。

然后立刻接下一步：我打算先找 3–5 个有公众号的同学试，收集"哪版更像"的反馈，并补一个盲评实验把效果量化。

> 这是当前最大的短板。搜索到的招聘经验里，"有别人真的用过"是权重最高的信号，而现在是 0。见第 6 节的补强计划。

### Q10 这个项目最难的部分是什么？

不是调模型，是**把"像"这个主观感受翻译成模型能执行的约束**。

"口语化一点"模型听不懂。要变成：平均段长多少字、最长段不超过多少、每几段一图、禁用哪些词、句长方差要多大。这个翻译过程没有标准答案，只能反复读原文、统计、试生成、看哪里不对、再调。

第二个难的是**去 AI 味改写怎么保证不跑偏**——最后靠三重校验 + 回退解决。

### Q11 你一个人做的？AI 帮了多少？（2026 年必问，务必诚实）

建议这样答：

> AI 参与了编码，包括脚手架生成和排错。但架构决策、风格量化的口径定义、微信适配规则、测试设计是我定的——每一条规则为什么这么定，我都能说清楚。AI 写的代码我会自己写断言验证，过程中改掉过它的问题（比如它第一次实现的多篇汇总直接累加计数，而各篇段数不同会引入偏差，我改成了按篇平均比例；还有短句成段锚点被 ≥8 字的过滤条件永久过滤掉，是测试发现的）。

**不要说"全部手写"，也不要说"主要是 AI 写的"。** 现在的面试官更关心你能不能维护、解释、改进这份代码，而不是它最初是谁敲的。承认 AI 参与但说清你的判断点，是最稳的姿态。

### Q12 如果重做，你会改什么？

- 早期就该定测试策略。项目前中期是靠手动点，后期才补测试，回头补的代价很大。
- 风格档案的 schema 应该一开始就带版本号。后来加选题/立场字段时靠"缺字段返回空串"做向后兼容，能工作但很别扭。
- 效果评估应该和开发同步做，而不是做完了才发现没法量化。

> 承认设计债 + 说清怎么还 = 成熟信号。

## 5. 必须避开的写法

| 别这么写 | 原因 | 改成 |
| --- | --- | --- |
| "训练了一个文风大模型" | 你没训练，一问就穿 | "设计风格量化规则并注入提示词" |
| "精通大模型 / 熟悉 AI 算法" | 空话，且会被深挖 | "OpenAI 兼容接口对接、提示词工程、输出结构化校验" |
| "高并发 / 分布式 / 微服务" | 项目里一个都没有 | 删掉，写"零依赖、可审计的规则引擎" |
| "用户量过万 / 广受好评" | 现在是 0，造假风险极高 | 写"自用 + 计划小规模试用"，或用真实数字（998 张图 / 184 张重复） |
| 把"148 条测试"写成"完善的测试体系" | 夸大 | 写具体：124 前端断言 + 24 端到端 |

**核心原则**：这个项目最值钱的是**真实**，不是宏大。你所有的优势都建立在"这是个真问题、我真的做完了、我能讲清每个决定"之上。一旦夸大，优势清零。

## 7. 讲述脚本

### 30 秒版（电梯 / 自我介绍用）

> 我做了一个让 AI 写公众号能像某个号本人写的工具。做法是抓这个号的历史文章，把文风按六层框架量化成参数，再从原文里挑真实段落当范例注入提示词；生成之后做一次去 AI 味的改写并做三重校验，不通过就回退；最后导出成能直接粘进微信后台的排版。全部跑在本机，零依赖，148 条测试。

### 3 分钟版（"介绍一下你的项目"）

1. **问题（20 秒）**：AI 写公众号有三类硬伤——风格不可描述、篇幅不可控、配图排版全靠手；现有开源工具只解决"写好之后怎么排"，不解决"怎么写"。
2. **方案（60 秒）**：四步——量化（六层框架统计成参数）→ 检索范例（按段落用途挑真实段落作锚点）→ 约束生成 + 去 AI 味改写（三重校验回退）→ 导出适配（微信后台限制反向变成规则）。
3. **关键取舍（40 秒）**：为什么不用微调（数据、定位、可解释性三条）+ 为什么零依赖单文件（用户是运营，双击即用）。
4. **踩的坑（40 秒）**：微信后台四个限制，尤其是"图片上方 0/46 插空段、下方 43/46 插空段"——这个不对称是数出来的。
5. **结果与边界（20 秒）**：148 条测试、图池实测数据；然后主动说已知限制（事实准确性无法根除、单机、2–3 分钟生成）。

**讲述原则**：问题 → 取舍 → 踩坑 → 结果。绝不按技术栈顺序讲。

## 8. 一句话自检

面试前用这三个问题自检：

1. 简历上每一句话，我能不能撑住三追问？
2. 我有没有把"为什么这么做"讲得比"做了什么"更多？
3. 我承认的短板，是不是都配了一个下一步方案？

三个都是"是"，这个项目就能稳稳站住。
